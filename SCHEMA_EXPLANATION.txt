=====================================================
  อธิบาย Database Schema — Musicky
  ไฟล์: backend/prisma/schema.prisma
=====================================================

ระบบของเราใช้ฐานข้อมูล PostgreSQL ผ่าน Prisma ORM
มีทั้งหมด 16 Model ที่ทำงานร่วมกัน ขออธิบายทีละตัวเลยนะครับ

─────────────────────────────────────────────────────
1. User — ตัวกลางหลักของระบบทั้งหมด
─────────────────────────────────────────────────────

  Relationship : เชื่อมกับเกือบทุก Model (1:N หรือ 1:1)
  เหตุผล       : ทุกกิจกรรมในแอปผูกกับผู้ใช้เสมอ

  Field สำคัญ:
  ┌─────────────────────┬──────────────────────────────────────────────┐
  │ Field               │ ความหมาย                                     │
  ├─────────────────────┼──────────────────────────────────────────────┤
  │ role                │ USER / ADMIN แยกสิทธิ์การใช้งาน              │
  │ isPremium           │ เช็คสิทธิ์ดาวน์โหลดเพลง                     │
  │ premiumExpiresAt    │ วันหมดอายุ Premium                           │
  │ isActive            │ แบน User โดยไม่ต้องลบข้อมูล                 │
  │ lastLogin           │ บันทึกเวลาล็อกอินล่าสุด                     │
  └─────────────────────┴──────────────────────────────────────────────┘

คำอธิบาย:
Model นี้สำคัญที่สุด เพราะเกือบทุก Model ในระบบต้องอ้างอิงกลับมาหา User
เก็บข้อมูลพื้นฐาน เช่น ชื่อ อีเมล รหัสผ่านที่ hashed แล้ว และ role ว่าเป็น USER หรือ ADMIN

ที่น่าสนใจคือมีฟิลด์ isPremium กับ premiumExpiresAt
สองตัวนี้คือสิ่งที่ระบบใช้ตรวจสอบว่าคนนี้มีสิทธิ์ดาวน์โหลดเพลงได้ไหม
ถ้า isPremium เป็น true และยังไม่หมดอายุ ก็ดาวน์โหลดได้เลย

มี isActive ไว้สำหรับแบน User โดยไม่ต้องลบข้อมูลออกจากระบบ
และมี lastLogin บันทึกว่าเข้าใช้งานครั้งล่าสุดเมื่อไหร่

─────────────────────────────────────────────────────
2. UserPreference — การตั้งค่าส่วนตัว
─────────────────────────────────────────────────────

  Relationship : User ──── UserPreference (1:1)
  เหตุผล       : แยกออกเพื่อไม่ให้ตาราง User บวม และ query เร็วขึ้น

  Field สำคัญ:
  ┌─────────────────────┬──────────────────────────────────────────────┐
  │ Field               │ ความหมาย                                     │
  ├─────────────────────┼──────────────────────────────────────────────┤
  │ streamingQuality    │ คุณภาพการ stream เพลง (Normal/High)          │
  │ downloadQuality     │ คุณภาพไฟล์ที่ดาวน์โหลด                      │
  │ musicLanguages      │ ภาษาเพลงที่ชอบ (array: Thai, English ฯลฯ)   │
  │ autoPlay            │ เล่นต่อเนื่องอัตโนมัติหรือไม่               │
  │ showLyrics          │ แสดงเนื้อเพลงอัตโนมัติหรือไม่               │
  └─────────────────────┴──────────────────────────────────────────────┘

คำอธิบาย:
เชื่อมกับ User แบบ 1 ต่อ 1 คือ User หนึ่งคนมี Preference ได้แค่ 1 ชุด
เก็บการตั้งค่าของแต่ละคน เช่น คุณภาพ streaming คุณภาพดาวน์โหลด
ภาษาเพลงที่ชอบ เปิด autoplay ไหม และแสดง lyrics อัตโนมัติไหม

เหตุผลที่แยกออกมาจาก User คือไม่อยากให้ตาราง User ใหญ่เกินไป
และเวลาดึงข้อมูล User ปกติก็ไม่จำเป็นต้องดึง preference มาด้วยทุกครั้ง

─────────────────────────────────────────────────────
3. RefreshToken — จัดการ Session การล็อกอิน
─────────────────────────────────────────────────────

  Relationship : User ──── RefreshToken[] (1:N)
  เหตุผล       : เก็บใน DB เพื่อให้ revoke ได้ทันที ต่างจาก JWT ทั่วไป

  Field สำคัญ:
  ┌─────────────────────┬──────────────────────────────────────────────┐
  │ Field               │ ความหมาย                                     │
  ├─────────────────────┼──────────────────────────────────────────────┤
  │ token               │ refresh token string (unique)                │
  │ expiresAt           │ อายุ 7 วัน                                   │
  └─────────────────────┴──────────────────────────────────────────────┘

คำอธิบาย:
ระบบเราใช้ JWT แบบ 2 ตัวคู่กัน
Access Token อายุ 1 ชั่วโมง และ Refresh Token อายุ 7 วัน

Refresh Token เก็บไว้ในฐานข้อมูล ไม่ใช่แค่ฝั่ง client
เพราะถ้าเก็บแค่ฝั่ง client เราจะ revoke หรือยกเลิก token ไม่ได้เลย
แต่พอเก็บใน DB ถ้า logout หรือพบการใช้งานผิดปกติ
ก็แค่ลบ record นั้นออก token นั้นก็ใช้ไม่ได้ทันที

User 1 คนมี RefreshToken ได้หลายอัน เพราะล็อกอินได้จากหลายเครื่อง

─────────────────────────────────────────────────────
4. Song — เพลง หัวใจหลักของ content ทั้งหมด
─────────────────────────────────────────────────────

  Relationship :
    Artist ──── Song ──── Album
    Genre  ────/

  เหตุผล : เพลงต้องมีเจ้าของ (Artist) หมวด (Genre) และชุด (Album) เสมอ

  Field สำคัญ:
  ┌─────────────────────┬──────────────────────────────────────────────┐
  │ Field               │ ความหมาย                                     │
  ├─────────────────────┼──────────────────────────────────────────────┤
  │ filePath            │ Cloudinary URL ของไฟล์เสียง                  │
  │ coverUrl            │ รูปปกเพลง                                    │
  │ duration            │ ความยาวเพลง (วินาที)                         │
  │ playCount           │ จำนวนครั้งที่เปิดฟัง                        │
  │ lyrics              │ เนื้อเพลง (synced หรือ plain text)           │
  └─────────────────────┴──────────────────────────────────────────────┘

คำอธิบาย:
เพลงทุกเพลงต้องผูกกับ Artist, Album และ Genre เสมอ เป็น required field
เก็บ filePath ซึ่งเป็น URL ของไฟล์เสียงบน Cloudinary
มี coverUrl สำหรับรูปปก duration ความยาวเพลง และ playCount จำนวนครั้งที่เปิดฟัง

Song เชื่อมกับหลาย Model พร้อมกัน
ถ้า User กดถูกใจ   → สร้าง record ใน LikedSong
ถ้า User เพิ่มใน playlist → สร้าง record ใน PlaylistSong
ถ้า User ดาวน์โหลด → สร้าง record ใน Download
ถ้า User เปิดฟัง   → สร้าง record ใน PlayHistory

5. Artist — ศิลปิน
─────────────────────────────────────────────────────

  Relationship :
    Artist ──── Song[]        (1:N)
    Artist ──── Album[]       (1:N)
    Artist ──── ArtistFollow[] ←── User

  เหตุผล : ศิลปินเป็น metadata หลักของเพลง User ติดตามได้

  Field สำคัญ:
  ┌─────────────────────┬──────────────────────────────────────────────┐
  │ Field               │ ความหมาย                                     │
  ├─────────────────────┼──────────────────────────────────────────────┤
  │ name                │ ชื่อศิลปิน                                   │
  │ bio                 │ ประวัติย่อ                                   │
  │ imageUrl            │ รูปภาพศิลปิน                                 │
  └─────────────────────┴──────────────────────────────────────────────┘

คำอธิบาย:
เก็บชื่อศิลปิน bio และรูปภาพ
Artist 1 คนมีได้หลายเพลงและหลายอัลบัม
User สามารถติดตามศิลปินได้ผ่าน Model ArtistFollow

─────────────────────────────────────────────────────
6. Album — อัลบัม
─────────────────────────────────────────────────────

  Relationship :
    Artist ──── Album ──── Song[]
    (N:1)            (1:N)

  เหตุผล : อัลบัมเป็น container รวมเพลงของศิลปิน

  Field สำคัญ:
  ┌─────────────────────┬──────────────────────────────────────────────┐
  │ Field               │ ความหมาย                                     │
  ├─────────────────────┼──────────────────────────────────────────────┤
  │ title               │ ชื่ออัลบัม                                   │
  │ releaseDate         │ วันที่วางจำหน่าย                             │
  │ coverUrl            │ รูปปกอัลบัม                                  │
  └─────────────────────┴──────────────────────────────────────────────┘

คำอธิบาย:
อัลบัมเป็นของ Artist คนเดียว และมีได้หลายเพลง
มี releaseDate บอกวันที่วางจำหน่าย
เวลาดึงเพลงมาแสดง จะ include Album มาด้วยเพื่อแสดงชื่ออัลบัมและรูปปก

─────────────────────────────────────────────────────
7. Genre — หมวดหมู่เพลง
─────────────────────────────────────────────────────

  Relationship : Genre ──── Song[] (1:N)
  เหตุผล       : จัดกลุ่มเพลงและแสดงผลในหน้า Home

  Field สำคัญ:
  ┌─────────────────────┬──────────────────────────────────────────────┐
  │ Field               │ ความหมาย                                     │
  ├─────────────────────┼──────────────────────────────────────────────┤
  │ name                │ ชื่อหมวด (unique)                            │
  │ imageUrl            │ รูปภาพประจำ Genre                            │
  │ color               │ สีสำรองกรณีไม่มีรูป (ใช้ใน Mosaic Gradient) │
  └─────────────────────┴──────────────────────────────────────────────┘

คำอธิบาย:
เพลงทุกเพลงต้องมี Genre 1 อัน
Genre มี imageUrl และ color สำหรับแสดงผลในหน้า Home
ที่เห็นเป็น Mosaic Gradient แต่ละสีต่างกันก็มาจากฟิลด์ color ตรงนี้

─────────────────────────────────────────────────────
8. Playlist + PlaylistSong — เพลย์ลิสต์ของ User
─────────────────────────────────────────────────────

  Relationship :
    User ──── Playlist ──── PlaylistSong ──── Song
                       (junction table / many-to-many)

  เหตุผล : 1 เพลงอยู่ได้หลาย Playlist, 1 Playlist มีได้หลายเพลง

  Field สำคัญ (PlaylistSong):
  ┌─────────────────────┬──────────────────────────────────────────────┐
  │ Field               │ ความหมาย                                     │
  ├─────────────────────┼──────────────────────────────────────────────┤
  │ position            │ ลำดับเพลงใน playlist                         │
  │ unique[playlistId,  │ ป้องกันเพลงซ้ำใน playlist เดียวกัน          │
  │        songId]      │                                              │
  └─────────────────────┴──────────────────────────────────────────────┘

คำอธิบาย:
Playlist เป็น container ที่ User สร้างขึ้น เช่น "เพลงเช้า" หรือ "Chill Vibes"
PlaylistSong คือ junction table ที่เชื่อม Playlist กับ Song แบบ many-to-many
หมายความว่า 1 เพลงอยู่ได้หลาย Playlist และ 1 Playlist มีได้หลายเพลง

มีฟิลด์ position เพื่อเรียงลำดับเพลงในเพลย์ลิสต์
และมี unique constraint ป้องกันเพลงซ้ำใน playlist เดียวกัน

─────────────────────────────────────────────────────
9. LikedSong — เพลงที่กดถูกใจ
─────────────────────────────────────────────────────

  Relationship : User ──── LikedSong ──── Song (many-to-many)
  เหตุผล       : เก็บรายการเพลงโปรดของแต่ละ User

  Constraint สำคัญ:
    @@unique([userId, songId]) — กด Like ซ้ำไม่ได้

คำอธิบาย:
junction table ระหว่าง User กับ Song
User 1 คนกด Like เพลงหนึ่งได้แค่ครั้งเดียว เพราะมี unique constraint คู่ [userId, songId]
รายการเพลงที่ถูกใจทั้งหมดจะแสดงในหน้า Library ของแอป

─────────────────────────────────────────────────────
10. Download — ประวัติการดาวน์โหลด
─────────────────────────────────────────────────────

  Relationship : User ──── Download ──── Song
  เหตุผล       : ตรวจสอบสิทธิ์และเก็บประวัติดาวน์โหลด

  Field สำคัญ:
  ┌─────────────────────┬──────────────────────────────────────────────┐
  │ Field               │ ความหมาย                                     │
  ├─────────────────────┼──────────────────────────────────────────────┤
  │ downloadedAt        │ วันเวลาที่ดาวน์โหลด                         │
  └─────────────────────┴──────────────────────────────────────────────┘

คำอธิบาย:
บันทึกว่า User คนไหนดาวน์โหลดเพลงไหนไปแล้วบ้าง
ก่อนดาวน์โหลด service จะตรวจ isPremium ก่อนเสมอ
ถ้าไม่ใช่ premium จะถูก block ก่อนที่จะมาถึงขั้นตอนสร้าง record นี้

─────────────────────────────────────────────────────
11. SearchHistory + SearchHistoryItem — ประวัติการค้นหา
─────────────────────────────────────────────────────

  Relationship :
    User ──── SearchHistory[]      (query string ที่พิมพ์)
    User ──── SearchHistoryItem[]  (item ที่กดเลือก)

  เหตุผล : แยก 2 ตารางเพราะ query กับ item ที่กดคือคนละเรื่องกัน

  Field สำคัญ (SearchHistoryItem):
  ┌─────────────────────┬──────────────────────────────────────────────┐
  │ Field               │ ความหมาย                                     │
  ├─────────────────────┼──────────────────────────────────────────────┤
  │ itemType            │ ประเภท: Song / Artist / Album                │
  │ title + subtitle    │ ชื่อที่แสดงในรายการ history                 │
  │ coverUrl            │ รูปปกสำหรับแสดง                             │
  └─────────────────────┴──────────────────────────────────────────────┘

คำอธิบาย:
แยกเป็น 2 ตาราง
SearchHistory เก็บ query string ที่พิมพ์ค้นหา เช่น "BTS" หรือ "ลูกทุ่ง"
SearchHistoryItem เก็บ item ที่ user กดเลือกจากผลการค้นหา
พร้อมกับ itemType ว่ากดเลือก Song หรือ Artist หรือ Album

─────────────────────────────────────────────────────
12. ArtistFollow — การติดตามศิลปิน
─────────────────────────────────────────────────────

  Relationship : User ──── ArtistFollow ──── Artist (many-to-many)
  เหตุผล       : User ติดตามศิลปินได้หลายคน ศิลปินมีผู้ติดตามได้หลายคน

  Constraint สำคัญ:
    @@unique([userId, artistId]) — follow ซ้ำไม่ได้

คำอธิบาย:
junction table ระหว่าง User กับ Artist
User ติดตามศิลปินได้หลายคน และศิลปิน 1 คนมีผู้ติดตามได้หลายคน
unique constraint ป้องกัน follow ซ้ำ

13. PlayHistory — ประวัติการฟังเพลง
─────────────────────────────────────────────────────

  Relationship : User ──── PlayHistory ──── Song
  เหตุผล       : สร้างส่วน "Recently Played" บนหน้า Home

  Field สำคัญ:
  ┌─────────────────────┬──────────────────────────────────────────────┐
  │ Field               │ ความหมาย                                     │
  ├─────────────────────┼──────────────────────────────────────────────┤
  │ playedAt            │ เวลาที่เปิดฟัง เรียงจากล่าสุดมาก่อน         │
  └─────────────────────┴──────────────────────────────────────────────┘

คำอธิบาย:
บันทึกทุกครั้งที่ User เปิดเพลง
ใช้สร้างส่วน "Recently Played" ในหน้า Home
เรียงจาก playedAt ล่าสุดมาก่อน

─────────────────────────────────────────────────────
14. Ads — โฆษณา
─────────────────────────────────────────────────────

  Relationship : ไม่เชื่อมกับ User (standalone)
  เหตุผล       : Admin จัดการโฆษณาเองฝ่ายเดียว

  Field สำคัญ:
  ┌─────────────────────┬──────────────────────────────────────────────┐
  │ Field               │ ความหมาย                                     │
  ├─────────────────────┼──────────────────────────────────────────────┤
  │ priority            │ 1–10 ยิ่งสูงยิ่งได้แสดงก่อน                 │
  │ startDate/endDate   │ ช่วงเวลาที่โฆษณาใช้งานได้                   │
  │ isActive            │ เปิด/ปิดโฆษณา                               │
  │ impressions         │ จำนวนครั้งที่แสดง                           │
  └─────────────────────┴──────────────────────────────────────────────┘

คำอธิบาย:
ตารางเดี่ยว ไม่เชื่อมกับ User เลย
Admin จัดการผ่าน WebAdmin กำหนดวันเริ่มต้น วันสิ้นสุด และ priority
แอปดึงโฆษณาที่ active และอยู่ในช่วงเวลาที่กำหนดมาแสดง
priority ยิ่งสูงยิ่งได้แสดงก่อน

15. Notification — การแจ้งเตือน
─────────────────────────────────────────────────────

  Relationship : User ──── Notification[] (1:N)
  เหตุผล       : แจ้งผลการชำระเงิน การเปิด Premium และการตอบ ticket

  type enum:
    PAYMENT_SUCCESS / PAYMENT_PENDING / PAYMENT_FAILED
    PREMIUM_ACTIVATED / PREMIUM_EXPIRING
    SUPPORT_REPLY

  Field สำคัญ:
  ┌─────────────────────┬──────────────────────────────────────────────┐
  │ Field               │ ความหมาย                                     │
  ├─────────────────────┼──────────────────────────────────────────────┤
  │ type                │ ประเภทการแจ้งเตือน (enum)                    │
  │ isRead              │ อ่านแล้วหรือยัง                             │
  │ amount              │ จำนวนเงิน (กรณีเป็น notification ชำระเงิน)  │
  └─────────────────────┴──────────────────────────────────────────────┘

คำอธิบาย:
เก็บ notification ของแต่ละ User
เมื่อ Admin อนุมัติการชำระเงิน ระบบจะสร้าง Notification ให้ User อัตโนมัติ
มีฟิลด์ isRead บอกว่าอ่านแล้วหรือยัง

16. PaymentTransaction — การชำระเงิน Premium
─────────────────────────────────────────────────────

  Relationship : User ──── PaymentTransaction[] (1:N)
  เหตุผล       : เก็บ history การสมัคร Premium ทุก transaction

  status enum  : PENDING → SUCCESS / FAILED
  method enum  : QR_CODE / BANK_TRANSFER

  Field สำคัญ:
  ┌─────────────────────┬──────────────────────────────────────────────┐
  │ Field               │ ความหมาย                                     │
  ├─────────────────────┼──────────────────────────────────────────────┤
  │ slipUrl             │ URL รูปสลิปที่ User แนบมา                    │
  │ accountName/No      │ ชื่อ-เลขบัญชีที่โอน                         │
  │ amount              │ ยอดชำระ (default 149 บาท)                    │
  └─────────────────────┴──────────────────────────────────────────────┘

คำอธิบาย:
เก็บทุก transaction ที่ User ส่งมาขอสมัคร Premium
User แนบ slip → Admin ตรวจสอบ → เปลี่ยน status เป็น SUCCESS
จากนั้น backend จะอัปเดต isPremium ใน User เป็น true และกำหนด premiumExpiresAt

─────────────────────────────────────────────────────
17. SupportTicket + SupportMessage — ระบบ Support
─────────────────────────────────────────────────────

  Relationship :
    User ──── SupportTicket ──── SupportMessage[]

  เหตุผล : แยก Ticket (หัวข้อ) กับ Message (ข้อความ) เพื่อรองรับ chat หลายรอบ

  status enum (Ticket) : OPEN → IN_PROGRESS → RESOLVED / CLOSED
  sender enum (Message): USER / ADMIN

  Field สำคัญ:
  ┌─────────────────────┬──────────────────────────────────────────────┐
  │ Field               │ ความหมาย                                     │
  ├─────────────────────┼──────────────────────────────────────────────┤
  │ subject             │ หัวข้อปัญหา                                  │
  │ status              │ สถานะ ticket                                 │
  │ sender              │ USER หรือ ADMIN เป็นคนส่งข้อความ             │
  │ content             │ เนื้อหาข้อความ                               │
  └─────────────────────┴──────────────────────────────────────────────┘

คำอธิบาย:
SupportTicket คือหัวข้อปัญหาที่ User เปิดขึ้นมา มี subject และ status
SupportMessage คือข้อความในแต่ละ ticket
sender เป็น enum ว่าเป็น USER หรือ ADMIN เป็นคนส่งข้อความ
ทำให้หน้า chat แยกได้ว่าข้อความไหนมาจากใคร
